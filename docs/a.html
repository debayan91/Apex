1. Backend Tech Stack & Server Infrastructure

  • Languages & Runtimes:
    • Java: Version 17 (OpenJDK 17 target/source bytecode).
    • Python: Version 3.x (used for orchestration and automation scripts such as start.py).
    • Node.js: Used for running k6/load-testing scripts (load-test.js).
  • Frameworks & Libraries:
    • Core Server Framework: Spring Boot 3.2.2 (org.springframework.boot:spring-boot-starter-parent).
    • Web & Networking: Spring Boot Starter Web (Embedded Tomcat, Spring MVC), Spring Boot Starter WebFlux (Reactor Netty client for non-blocking reactive WebSocket streaming).
    • ORM & Persistence: Spring Boot Starter Data JPA, Hibernate 6.x, PostgreSQL JDBC Driver (org.postgresql:postgresql).
    • Validation: Jakarta Bean Validation via spring-boot-starter-validation (Hibernate Validator).
    • Code Generation: Project Lombok (org.projectlombok:lombok) for automated builder patterns, getters, setters, and logging injection.
    • Testing Tools: Spring Boot Starter Test (JUnit 5, Mockito, AssertJ, Spring Test Context).
  • Databases & Caching:
    • Primary Relational Database: PostgreSQL (port 5432, database name heron_db) configured with Hibernate DDL auto-update for persistent entities.
    • In-Memory Caching: Redis (port 6379) via spring-boot-starter-data-redis (Lettuce client driver) utilizing @RedisHash("LatestPrice") for microsecond price lookups.
    • Message Broker: Apache Kafka (port 9092) via spring-kafka for real-time market event streaming on the market-ticks topic with JSON serialization/deserialization.
    • Vector Stores: None present in this architecture.
  • DevOps & External Integrations:
    • Docker & Container Configurations: Multi-service docker-compose.yml provisioning isolated local containers for PostgreSQL, Redis, Apache Kafka, and Zookeeper.
    • Build Tooling: Apache Maven 3.x with Maven Wrapper (mvnw) and Spring Boot Maven Plugin.
    • External APIs & Feeds: Live public Binance WebSocket stream (wss://stream.binance.com:9443/ws/btcusdt@trade) feeding BTC/USDT transaction ticks directly into the messaging ingestion pipeline.

3. Backend Features & API Inventory

  • API Endpoints & Handlers:
    • POST /api/orders: Submits a new buy/sell order.
      • Header: Idempotency-Key (Required, UUID).
      • Payload: { "userId": Long, "symbol": String, "side": "BUY"|"SELL", "quantity": Integer, "strategyType": String }.
      • Logic: Performs idempotency verification, validates bean constraints, queries live Redis price, evaluates algorithmic strategy (if passed), invokes risk checks, transitions states via OrderStateMachine, executes atomic balance deductions with pessimistic locking, adjusts asset holdings, and records audit trails.
    • GET /api/orders/history/{userId}: Returns historical list of orders placed by a specific user.
    • GET /api/strategies: Returns registered strategy names (e.g. ["Simple Moving Average (SMA)"]).
    • POST /api/strategies/{name}/signal: Analyzes historical ticks from market_tick to generate actionable buy/sell/hold trading signals with confidence scores.
    • POST /api/strategies/backtest: Simulates algorithmic trading execution over a historical date-time range and calculates total return percentage, max drawdown, and trade count.
    • GET /portfolio/{userId}: Calculates the complete portfolio summary including available cash, active symbol positions, average buy prices, and mark-to-market total portfolio valuation.
    • POST /user/create: Registers a new user identity and provisions an associated wallet with initial capital.
    • GET /user/{id}: Retrieves user account information.
    • POST /user/{id}/deposit: Credits user balance via WalletService with pessimistic locking and writes an entry to transaction_ledger.
    • GET /user/{id}/wallet: Retrieves user wallet cash balance.
    • GET /prices/latest?symbol={symbol}: Fetches cached latest price from Redis (or returns all symbols if omitted).
  • Background Jobs & Pipelines:
    • Binance WebSocket Streamer (BinanceWebSocketClient): Runs continuously via Reactor Netty on application startup (ApplicationReadyEvent), subscribing to btcusdt@trade. Includes exponential backoff reconnection logic (up to 10 retries, max 60s backoff) and publishes incoming trades to Kafka.
    • Kafka Market Tick Consumer (MarketTickKafkaConsumer): Subscribes to the market-ticks Kafka topic and dispatches events to MarketTickPersistenceHandler.
    • Market Tick Ingestion Pipeline (MarketTickPersistenceHandler): Asynchronously ingests ticks, calculates end-to-end pipeline latency, persists ticks to PostgreSQL (market_tick), and upserts the Redis LatestPrice cache.
    • Cold-Start Seeding (DataInitializer): Implements CommandLineRunner to bootstrap default accounts (pro_trader with $1,000,000) and fallback prices for BTCUSDT and ETHUSDT if the datastore is empty.
  • Security & Middleware:
    • Pessimistic Concurrency Locking: WalletRepository.findWalletByUserId acquires a PESSIMISTIC_WRITE row-level lock on database operations to avoid balance race conditions during concurrent order executions or deposits.
    • Idempotent Operations: Unique constraint enforcement on orders.idempotency_key guarantees single-execution semantics.
    • Risk Validation Engines: RiskManagementService enforces fat-finger caps ($1,000,000 max single order value) and prevents concurrent wash trades. RiskGuard validates post-trade minimum capital thresholds ($100.00) and caps maximum daily trades at 50 per user.
    • State Machine Integrity: OrderStateMachine strictly forbids illegal status skips (only PENDING_VALIDATION → VALIDATED → FILLED or REJECTED are permitted).
    • Global Exception Translation: GlobalExceptionHandler intercepts unhandled domain exceptions (e.g. InsufficientBalanceException, RiskViolationException, MethodArgumentNotValidException) and normalizes responses into standardized HTTP error objects.

4. Server-Side Architecture & Request Lifecycle

The backend is built around a layered architecture featuring transactional boundaries, concurrency control, and asynchronous event streams:

1. HTTP Request Arrival: An incoming client request (e.g. POST /api/orders) hits the Spring DispatcherServlet and is routed to OrderController. Jakarta Bean Validation inspects DTO constraints (such as positive quantities, required symbols, valid Enums).

2. Service Orchestration & Idempotency: OrderExecutionService checks OrderRepository.findByIdempotencyKey(...). If the key exists, it short-circuits and immediately returns the cached order. Otherwise, a new record is initialized in the database under PENDING_VALIDATION.

3. Market Price & Strategy Verification: The service queries MarketDataService to retrieve the live price from Redis. If a strategy name is supplied in the request, the strategy is looked up from Spring's injected bean map and executed against the tick. If the strategy signal disagrees with the requested trade direction (e.g. strategy signals HOLD while request is BUY), execution fails fast.

4. Risk Assessment: RiskManagementService evaluates if the trade exceeds the $1M fat-finger threshold or duplicates an existing active trade. Additionally, available wallet balance or holding share counts are validated before acquiring locks.

5. Order State Machine Transition to VALIDATED: OrderStateMachine.transition(order, VALIDATED) writes an audit trail to order_audit_logs.

6. Database Transaction & Pessimistic Lock Settlement: Under a @Transactional boundary, WalletService.adjustBalance requests a PESSIMISTIC_WRITE lock on the user's wallet row, adjusts the balance, and inserts an audit record into transaction_ledger. Holdings are subsequently updated (or inserted/deleted) via HoldingRepository with a recalculated volume-weighted average price.

7. Fulfillment & Final State: The order execution price and completion timestamp are saved, and the state machine transitions the order from VALIDATED → FILLED, committing the transaction and returning the final payload to the client.
